# Scripture Search MVP

1. **Prepare the pilot.** Start with the local Vijñāna Bhairava Markdown witnesses and Ānandabhaṭṭa commentary. Confirm source identity, permitted use, OCR status and stable locators for each input. Preserve the hierarchy actually present in each source. Keep edition-specific numbering, untouched quotations and reviewed commentary links. Store language, script, title aliases and normalized search forms separately from the source text.
2. **Run the Legal-AI baseline.** Map each verse or coherent passage into Legal-AI’s portable JSONL interchange format, retaining the source and locator. Keep Markdown as the canonical corpus. Run exact references and Tantivy keyword search, then add script and spelling normalization and character-level matching as measured improvements. Use parent and neighboring passages for context. [Legal-AI architecture](https://github.com/aispanda/Legal-AI/blob/main/docs/architecture.md)
3. **Compare retrieval on the same questions.** Freeze a held-out set with human-checked expected passages and no-match cases. Compare structure-aware lexical retrieval, direct multilingual dense search, search over aligned translations where available, and hybrid fusion. Test reranking and structure-based routing separately to see what each contributes. Use fresh scripture embeddings for vector experiments. Report top-rank accuracy, Recall@k, edition and locator correctness, false matches and local latency by query type. Select the simplest search configuration that meets the agreed criteria and measurably improves weak query categories. [Grok research](https://source-grounded-scripture-rag-state-of-kk26.pages.grok.bot/)
4. **Deliver a local search workflow.** Return inspectable evidence and distinguish an original verse from its translation, commentary or later retelling. Include reviewed links when available. Record unresolved alignments and missing coverage. Run independent checks on the selected build. Use the evaluation to plan the next corpus and language slices.

The Grok report’s small experiments give us candidates to reproduce. Normalized and character-level matching is worth testing for script variants, and the reported English-to-Sanskrit results make translation-assisted search a priority comparison. STAIR contributes a complementary idea. Retain work and section hierarchy in the MVP and test whether it improves routing or context. The published STAIR numbers are from SearchTome, an English textbook benchmark. A fine-tuned STAIR retriever remains an experiment rather than an MVP dependency.
