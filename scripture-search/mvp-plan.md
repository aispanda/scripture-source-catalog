# Scripture Search MVP

1. **Reconcile the catalogue and prepare Markdown.** Account for each title, edition and volume in the priority source lists. Select source-backed Vijñāna Bhairava witnesses and Ānandabhaṭṭa commentary for the first slice. Confirm source identity, permitted use, OCR status and locators. Preserve the hierarchy, edition-specific numbering, wording and reviewed commentary links. Keep search aliases and provenance separately. Record unresolved conversion or rights exceptions. Store eligible Markdown in the private corpus bucket and verify its object URI and checksum before writing the catalogue pointer. [SCR-01 catalogue](../story.md) · [Ingestion and cloud status](story.md#execution-record)
2. **Verify Legal-AI reuse and prepare pilot records.** Exercise the existing importer with a small fixture, then map every verified verse or coherent passage into its portable JSONL contract. Keep edition, locator, neighboring passages, and the Markdown source in the trace. Prepare separate tuning and restricted held-out sets with human-checked expected and absent passages. Freeze the held-out set, metric targets and selection rule before tuning. [Legal-AI architecture](https://github.com/aispanda/Legal-AI/blob/main/docs/architecture.md)
3. **Run the lexical baseline.** Run exact references and Tantivy keyword search, then add script and spelling normalization and character-level matching using only the tuning set. Use parent and neighboring passages for context. [Legal-AI architecture](https://github.com/aispanda/Legal-AI/blob/main/docs/architecture.md)
4. **Compare retrieval on the same questions.** Freeze candidate configurations after tuning. Have a verifier compare structure-aware lexical retrieval, direct multilingual dense search, search over aligned translations where available, and hybrid fusion. Test reranking and structure-based routing separately. Use fresh scripture embeddings for vector experiments. Report top-rank accuracy, Recall@k, edition and locator correctness, false matches and local latency by query type. Select the simplest configuration that meets the agreed criteria. Choose hybrid only if it delivers the pre-agreed quality improvement over the best non-hybrid candidate within the agreed latency budget. Use a fresh holdout to verify any retuned candidate. [Grok research](https://source-grounded-scripture-rag-state-of-kk26.pages.grok.bot/)
5. **Deliver a local search workflow.** Return inspectable evidence and distinguish an original verse from its translation, commentary or later retelling. Include reviewed links when available. Record unresolved alignments and missing coverage. Run independent Codex task verification on the selected build, then formal end-to-end acceptance in a fresh Gemini Neon session in the standalone Google Antigravity App. Use the evaluation to plan the next corpus and language slices. [Acceptance scenarios](scenarios.json)

The Grok report’s small experiments give us candidates to reproduce. Test normalized and character-level matching for script variants, and compare translation-assisted search for English-to-Sanskrit queries. STAIR’s SearchTome results come from an English textbook benchmark. Retain work and section hierarchy and test whether it improves scripture routing or context.
